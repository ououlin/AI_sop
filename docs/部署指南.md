# 部署指南

> 三种部署形态：单机（工位试点）、多工位（整线）、SaaS 多租户（多客户托管）。
> 环境变量清单见 [配置参考](配置参考.md)。

## 1. 形态选择

| 形态 | 适用场景 | 数据存储 | 摄像头 |
|------|----------|----------|--------|
| 单机 | 单工位试点、演示 | SQLite | 宿主机直连 |
| 多工位 | 整条产线 | 每工位 SQLite；中央服务可 SQLite/PostgreSQL | 各工位宿主机直连 |
| SaaS 多租户 | 多客户托管 | PostgreSQL（可选 schema 隔离） | 工位端独立部署 |

> 识别流水线必须直接访问摄像头，因此**工位端建议跑在宿主机**；容器化适合中央聚合服务与 SaaS 服务端。

## 2. 单机部署（Windows 工位）

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\activate
pip install -r requirements.txt

copy .env.example .env        # 至少修改 JWT_SECRET、STATION_API_KEY
python main.py
```

前端二选一：

- 开发：`cd frontend && npm run dev`，访问 <http://localhost:5173>
- 生产：`cd frontend && npm run build`，后端会在 `/` 托管 `frontend/dist`

默认账号（租户 `default`）：`admin/admin123`、`supervisor/super123`、`operator/op123`。

## 3. 多工位部署

**工位端**（每台设备一份后端）：

```ini
ENABLE_LOCAL_AGGREGATION=false
CENTRAL_SERVER_URL=http://<中央服务器IP>:8000
STATION_ID=W-001
STATION_NAME=工位1
STATION_API_KEY=<与中央服务一致的共享密钥>
```

**中央端**（产线看板）：

```ini
ENABLE_LOCAL_AGGREGATION=true
STATION_API_KEY=<与工位一致的共享密钥>
```

中央端接收 `POST /api/v1/station/report`，对外提供 `/api/v1/stations`、`/api/v1/line/summary` 与「产线看板」面板。

> 若 `CENTRAL_SERVER_URL` 指向自身端口，服务会自动跳过上报避免 httpx 回环；自测时可设 `STATION_REPORT_TO_SELF=true` 强制上报。

## 4. Docker Compose（PostgreSQL）

面向服务端部署（中央聚合 / SaaS 数据面）。前端在构建阶段打包进镜像，由后端静态托管。

```bash
# 1. 准备环境变量（可选，未设置时使用开发默认值）
export POSTGRES_PASSWORD='strong-password'
export JWT_SECRET='long-random-secret'
export STATION_API_KEY='shared-station-key'
export PLATFORM_ADMIN_PASSWORD='platform-admin-password'

# 2. 构建并启动
docker compose up -d --build

# 3. 查看日志与健康状态
docker compose logs -f api
curl http://localhost:8000/api/v1/health
```

访问 <http://localhost:8000>，用 `platform / <PLATFORM_ADMIN_PASSWORD>` 登录（租户 `default`）即可在「平台管理」开通租户。

**说明**

- 容器内没有摄像头设备，工位识别请勿放容器；容器适合中央聚合与 SaaS 服务端
- 数据持久化在 `pgdata` 卷；删除卷会丢失全部租户与执行记录
- 首次启动会自动建表并写入默认租户与订阅；`PLATFORM_ADMIN_PASSWORD` 为空时不会创建平台管理员

## 5. PostgreSQL 与 schema 级隔离

`DATABASE_URL` 支持任意 SQLAlchemy PostgreSQL 连接串：

```ini
DATABASE_URL=postgresql+psycopg2://user:password@host:5432/ai_sop
```

默认使用公共 schema（行级 `tenant_id` 隔离）。若希望**一个部署只服务一个租户、物理隔离到独立 schema**：

```ini
DATABASE_URL=postgresql+psycopg2://user:password@host:5432/ai_sop
TENANT_SCHEMA=tenant_acme
```

启动时会自动 `CREATE SCHEMA IF NOT EXISTS`，并设置连接的 `search_path`，所有表建在该 schema 内。多个租户各自部署一套服务、指向同一数据库的不同 schema，即可实现 schema 级隔离。

> 该模式下 `tenants` 表也在各自 schema 内，租户开通仍由各自的平台管理员完成。

## 6. 生产检查清单

- [ ] `JWT_SECRET` 已改为长随机串（未配置时每次重启会随机生成，导致登录态失效）
- [ ] `STATION_API_KEY` 已配置且工位与中央端一致
- [ ] 默认账号 `admin/admin123` 等已修改或禁用
- [ ] HTTPS 部署时设置 `COOKIE_SECURE=true`
- [ ] 数据库与 `backend/data/` 已纳入备份（SQLite 迁移前会自动生成 `.db.bak`）
- [ ] 日志级别与轮转策略确认（`LOG_LEVEL`，文件在 `backend/logs/`）

## 7. 数据库迁移

两种方式按场景使用：

| 场景 | 方式 | 说明 |
|------|------|------|
| 本地开发（SQLite） | `schema.py` 幂等自举 | 启动自动建表、补列、回填默认租户，迁移前备份 `.db` |
| PostgreSQL / 生产 | Alembic | 表结构变更由 `alembic upgrade head` 管理，版本记录在 `alembic_version` |

```bash
cd backend
alembic upgrade head                        # 建表或升级到最新版本
alembic current                             # 查看当前版本
alembic revision --autogenerate -m "描述"   # 模型改动后生成迁移
```

**三种启动顺序都安全**：

1. 先 `alembic upgrade head` 再启动服务（推荐；Docker 镜像即此顺序）
2. 直接启动服务由 `schema.py` 建表 —— 之后执行一次 `alembic stamp head` 补版本记录
3. 旧版本服务已经建过表的库 —— 同样 `alembic stamp head` 一次即可
