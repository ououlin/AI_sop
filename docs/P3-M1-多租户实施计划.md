# P3-M1 · SaaS 多租户实施计划

> **状态**：🚧 进行中（阶段 0 已完成）　|　**周期**：2026-11 ~　|　**目标**：把单租户本地部署升级为多租户数据面
>
> 上级：[P3 商业化与规模化](P3-商业化与规模化.md) §4.1　·　[文档索引](README.md)

## 1. 范围

**做**：租户数据模型与隔离、租户管理与开通、套餐与配额、平台管理员视角、PostgreSQL 部署支持。

**不做**：真实支付扣费网关、租户自助注册与在线开通页面、计费发票。

**架构边界（重要）**：识别流水线（摄像头 → MediaPipe → 状态机）天然是**单工位单租户**的，一个进程只服务一台设备的画面。因此 M1 的多租户发生在**数据与管理面**：多租户共享同一套 API 与数据库，每个租户的工位 Agent 独立部署、按租户上报。不为单进程引入多路视频混跑。

## 2. 关键设计决策

| 编号 | 决策 | 理由 |
|------|------|------|
| D1 | **共享库 + `tenant_id` 行级隔离**作为默认实现；PostgreSQL schema 级隔离留作阶段 4 的可选部署形态 | SQLite 无 schema；行级隔离在现有部署上零迁移成本，配合数据访问层统一过滤与隔离测试可保证正确性 |
| D2 | 登录请求体带租户编码（缺省 `default`）→ JWT 携带 `tid` → 中间件写入请求级上下文 | 不引入子域名依赖，本地/内网部署同样可用；平台管理员可通过 `X-Tenant-Id` 跨租户 |
| D3 | 阶段 0-2 用幂等 `ensure_schema()` 自举，阶段 3 引入 Alembic 接管演进 | 保持 `python main.py` 开箱可用；Alembic 需要版本基线，放在模型稳定后更合适 |
| D4 | 存量数据全部回填到 `default` 租户（id=1） | 平滑升级，老部署升级后行为不变 |

## 4. 阶段详情

### 阶段 0 · 数据层地基（已完成）

| 文件 | 变更 |
|------|------|
| `backend/db_models.py` | 新增 `TenantDB`；`users` / `sop_definitions` / `execution_records` 增加 `tenant_id`；唯一约束改为 `(tenant_id, username)` / `(tenant_id, name)` |
| `backend/database.py` | 支持 `DATABASE_URL`（默认 SQLite），SQLite 专属参数按方言启用 |
| `backend/schema.py` | 幂等自举：建表 → 补列 → 回填 `default` → 重建唯一约束；迁移前自动备份 |
| `backend/tenancy/context.py` | 请求级租户上下文（`contextvars`） |
| `backend/middleware/tenant_middleware.py` | 从 JWT `tid` 解析租户并注入上下文，请求结束复位 |
| `backend/repositories/*.py` | 查询自动附加租户过滤；写入自动带上当前租户 |
| `backend/api/v1/auth.py` | 登录校验租户状态、Token 携带 `tid`、用户按租户过滤；`/auth/me` 同时支持 Cookie |
| `backend/tests/test_tenancy.py` | 上下文、租户内唯一、跨租户隔离、老库迁移、幂等、中间件 |

**验收**：老库自动升级且数据不丢；租户 A 看不到租户 B 的 SOP/记录/用户；全量 13 个用例通过；`python main.py` 正常启动。

### 阶段 1 · 租户管理与开通（进行中）

- `backend/saas/tenant_manager.py`：租户 CRUD、开通时创建管理员、启停用
- `backend/api/v1/tenant.py`：`/tenants` 列表、创建、详情、更新
- `backend/auth/role_checker.py`：新增 `platform_admin` 角色与 `tenant:view` / `tenant:manage` 权限
- 平台管理员通过 `X-Tenant-Id` 进入指定租户

**验收**：平台管理员可开租户并指定管理员账号；新租户登录后只见自己的数据；普通管理员无法调用租户接口。

### 阶段 2 · 订阅与配额

- `backend/saas/subscription.py`：套餐（免费/标准/专业/企业）、工位数与存储配额、到期时间
- 配额校验依赖：工位上报数超限拒绝、记录保留期清理
- `/tenant/{id}/subscription` 查询与变更

**验收**：超出工位数配额时上报返回 409；到期租户只读。

### 阶段 3 · 前端平台管理

- 登录页支持租户编码输入
- `frontend/src/pages/admin/TenantManagement.tsx`（租户列表、开通、配额）
- 平台管理员的租户切换器

### 阶段 4 · 部署形态与文档

- PostgreSQL 支持与 schema 级隔离模式
- Alembic 接管迁移
- 部署文档（Docker Compose：api + postgres + 前端）

## 5. 风险与对策

| 风险 | 对策 |
|------|------|
| 隔离遗漏导致跨租户越权 | 数据访问层统一过滤 + 专项隔离测试 + 代码评审清单 |
| SQLite 无法直接改唯一约束 | `schema.py` 重建表并保留自增 id，迁移前备份 `.db` 文件 |
| 老 Token 无 `tid` | 解析时缺省 `default` 租户，保证升级期间不掉线 |
| 单进程多租户误用 | 文档与日志明确「一个进程 = 一个工位」，不承诺单进程多路识别 |
